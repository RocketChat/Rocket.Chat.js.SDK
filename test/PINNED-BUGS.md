# Pinned bugs

Behaviour the specs assert **as it is today**, not as it should be. Each row is a
known defect: the spec exists so a future fix is a deliberate, visible change
rather than a silent one. When a row is fixed, change the spec and delete the row.

| # | Bug | Where | Pinned by | Notes |
| - | --- | ----- | --------- | ----- |
| 2 | The OAuth credential guard tests `params.oath` — a typo for `oauth` — and reads `credentialToken`/`credentialSecret` off the root instead of the `oauth` object. A well-formed `ICredentialsOAuth` therefore fails the guard and falls through to the password branch, where `sha256(undefined)` throws. | `interfaces/index.ts`, `isLoginOAuth` | `lib/drivers/ddp.spec.ts`, the OAuth branch | The spec passes the misspelled shape, because that is the only shape that reaches the branch. |
| 3 | The constructor builds `config.ping` from `options.timeout`, so a caller passing the option named `ping` — the name the config field and the ping timer both use — is silently ignored and gets whatever `timeout` says (or the 10000ms default when `timeout` is absent too). | `lib/drivers/ddp.ts`, `Socket` constructor | `lib/drivers/ddp.spec.ts`, `new Socket` | Wrong because the option that names the behaviour has no effect and fails silently: nothing warns, and the socket pings on an interval the caller never asked for. |
| 4 | `options` is declared optional (`options?`), but the constructor dereferences it immediately (`options.logger`), so `new Socket()` throws a `TypeError`. | `lib/drivers/ddp.ts`, `Socket` constructor | `lib/drivers/ddp.spec.ts`, `new Socket` | Wrong because the signature promises a no-argument construction that always crashes — every field it reads already has a default, so the optionality is meaningful and merely unimplemented. |
| 5 | `onMessage` parses the frame with an unguarded `JSON.parse`, so a malformed frame throws straight out of the callback. The `if (!data)` guard below it — which logs `[ddp] JSON parse error` — can therefore never see bad JSON; only a falsy `e.data` (an empty string) reaches it, and the message it logs reads `e.message`, which a websocket message event does not carry. | `lib/drivers/ddp.ts`, `onMessage` | `lib/drivers/ddp.onMessage.spec.ts` pins the throw. The empty-payload branch is recorded here rather than tested — testing it would assert a log line that describes something that did not happen. | Fixing means wrapping the parse in a `try`, which is a shipped-source change. |
| 6 | A failed reply rejects with the server's raw error payload, not an `Error`. Every caller that logs `err.message` — `call`, `subscribe`, `unsubscribe` — therefore logs `undefined` and loses the reason. | `lib/drivers/ddp.ts`, `send` | `lib/drivers/ddp.send.spec.ts`, the failed-reply case | Fixing it means wrapping the payload, which changes what callers receive; the spec asserts the payload identity so the change is visible. |
| 7 | A send issued while the socket is not open waits on the `open` event with no timeout, so it never settles — the caller hangs for the life of the process. The same path also drops the no-connection guard's `throw`, because it sits inside an async promise executor (see the `no-async-promise-executor` entry in `.oxlintrc.json`). | `lib/drivers/ddp.ts`, `send` | `lib/drivers/ddp.send.spec.ts`, the not-open case, driven ten minutes forward on the fake clock | Only the unbounded wait is pinned by a spec. The dropped `throw` cannot be: the rejection escapes as an unhandled rejection and fails the file whatever the test asserts. |
| 8 | `unsubscribe` rejects with the bare subscription id — a string — when the id is not in the map. Every caller reads `err.message`, which is undefined on a string, so the reason is lost — and `close` swallows it into a debug log. | `lib/drivers/ddp.ts`, `unsubscribe` | `lib/drivers/ddp.subscriptions.spec.ts`, the not-in-the-map case | Same shape as row 6 but a separate defect: this one is the driver's own rejection value, not the server's payload passed through. |
| 9 | `unsubscribe` deletes `subscriptions[id]` before sending the `unsub` frame, rather than on the server's acknowledgement. A refused or dropped unsubscribe therefore leaves the server still streaming while the driver can no longer name the subscription — it can neither retry nor resubscribe it after a reconnect. | `lib/drivers/ddp.ts`, `unsubscribe` | `lib/drivers/ddp.subscriptions.spec.ts`, the live-subscription cases | Fixing means moving the delete into the `then`, which changes what a concurrent `unsubscribeAll` sees mid-flight. |
| 10 | `send` writes `subscriptions[id]` under the *send-time* id for any `sub` frame, and `subscribe` then writes it again under the id the server returned in `subs[0]`. When the two differ, the send-time entry is orphaned: it is never acknowledged, never cleaned up, and `subscribeAll` resubscribes it forever. | `lib/drivers/ddp.ts`, `send` | Recorded here, not tested. The send-time write is pinned by `lib/drivers/ddp.driver.spec.ts` and the acknowledged-id keying by `lib/drivers/ddp.subscriptions.spec.ts`; a spec for the orphan would only assert that a server which renames ids is mishandled. | Fixing means `send` stops writing the map at all and `subscribe` owns it alone, which changes what an in-flight `unsubscribeAll` can see. |
| 11 | `DDPDriver`'s constructor writes `timeout: 10000` into its config *after* spreading the caller's options, so a caller-supplied `timeout` is discarded. Combined with row 3 — the socket reads its ping interval from `timeout` — the number a caller passes reaches nothing at all. | `lib/drivers/ddp.ts`, `DDPDriver` constructor | `lib/drivers/ddp.driver.spec.ts`, `new DDPDriver` | Wrong because it is silent: the option is accepted, typechecks, and is overwritten. Fixing it means letting the caller's value through, which changes the ping interval for anyone who passes one — hence the pin. |
| 12 | `connected` requires `alive()`, so an open socket whose last ping has gone stale reports itself disconnected. `close` gates the actual close on `connected`, so closing such a socket skips it entirely: the transport is abandoned still open, and the process leaks it. | `lib/drivers/ddp.ts`, `connected` and `close` | `lib/drivers/ddp.liveness.spec.ts`, the stale-ping cases | The two halves are one defect: liveness is being used as a proxy for "is there a socket to close", which it is not. Fixing means closing on the socket's own ready state rather than on `connected`. |
| 13 | `probe` snapshots `lastPing` and then ignores any pong unless the stamp *strictly* advances, so a server answering within the same millisecond is discarded and the probe times out on a demonstrably live socket. | `lib/drivers/ddp.ts`, `probe` | `lib/drivers/ddp.liveness.spec.ts`, the probe cases | Under the frozen test clock this is deterministic; in production it is a rare, unreproducible false negative. Fixing means comparing `>=`, or tracking the pong by identity rather than by timestamp. |
| 14 | `open` takes an interval argument (`_ms`, defaulted from `config.reopen`) and never reads it, so a caller passing one gets no effect at all: the retry after a dropped connection still waits `config.reopen`. | `lib/drivers/ddp.ts`, `open` | `lib/drivers/ddp.connection.spec.ts`, the interval-argument case | Wrong because the parameter is part of the public signature and silently inert. Fixing it means either honouring the argument — which changes the retry delay for anyone who passes one — or removing it, which is a breaking signature change; hence the pin. |
