# Pinned bugs

Behaviour the specs assert **as it is today**, not as it should be. Each row is a
known defect: the spec exists so a future fix is a deliberate, visible change
rather than a silent one. When a row is fixed, change the spec and delete the row.

| # | Bug | Where | Pinned by | Notes |
| - | --- | ----- | --------- | ----- |
| 1 | Importing the driver mutates `tiny-events` process-wide: it assigns `EventEmitter.prototype.removeAllListeners` at module scope, so every emitter in the host process — including ones the SDK never created — gets the replacement. It also returns `[]` instead of the removed listeners. | `lib/drivers/ddp.ts` (module top level) | `test/setup.ts` captures the pristine method before any spec import and restores it in teardown | Cannot be fixed without touching shipped source. The setup file contains the blast radius to one test file. |
| 2 | The OAuth credential guard tests `params.oath` — a typo for `oauth` — and reads `credentialToken`/`credentialSecret` off the root instead of the `oauth` object. A well-formed `ICredentialsOAuth` therefore fails the guard and falls through to the password branch, where `sha256(undefined)` throws. | `interfaces/index.ts`, `isLoginOAuth` | `lib/drivers/ddp.spec.ts`, the OAuth branch | The spec passes the misspelled shape, because that is the only shape that reaches the branch. |
| 3 | The constructor builds `config.ping` from `options.timeout`, so a caller passing the option named `ping` — the name the config field and the ping timer both use — is silently ignored and gets whatever `timeout` says (or the 10000ms default when `timeout` is absent too). | `lib/drivers/ddp.ts`, `Socket` constructor | `lib/drivers/ddp.spec.ts`, `new Socket` | Wrong because the option that names the behaviour has no effect and fails silently: nothing warns, and the socket pings on an interval the caller never asked for. |
| 4 | `options` is declared optional (`options?`), but the constructor dereferences it immediately (`options.logger`), so `new Socket()` throws a `TypeError`. | `lib/drivers/ddp.ts`, `Socket` constructor | `lib/drivers/ddp.spec.ts`, `new Socket` | Wrong because the signature promises a no-argument construction that always crashes — every field it reads already has a default, so the optionality is meaningful and merely unimplemented. |
| 5 | `onMessage` parses the frame with an unguarded `JSON.parse`, so a malformed frame throws straight out of the callback. The `if (!data)` guard below it — which logs `[ddp] JSON parse error` — can therefore never see bad JSON; only a falsy `e.data` (an empty string) reaches it, and the message it logs reads `e.message`, which a websocket message event does not carry. | `lib/drivers/ddp.ts`, `onMessage` | `lib/drivers/ddp.onMessage.spec.ts` pins the throw. The empty-payload branch is recorded here rather than tested — testing it would assert a log line that describes something that did not happen. | Fixing means wrapping the parse in a `try`, which is a shipped-source change. |
| 6 | A failed reply rejects with the server's raw error payload, not an `Error`. Every caller that logs `err.message` — `call`, `subscribe`, `unsubscribe` — therefore logs `undefined` and loses the reason. | `lib/drivers/ddp.ts`, `send` | `lib/drivers/ddp.send.spec.ts`, the failed-reply case | Fixing it means wrapping the payload, which changes what callers receive; the spec asserts the payload identity so the change is visible. |
| 7 | A send issued while the socket is not open waits on the `open` event with no timeout, so it never settles — the caller hangs for the life of the process. The same path also drops the no-connection guard's `throw`, because it sits inside an async promise executor (see the `no-async-promise-executor` entry in `.oxlintrc.json`). | `lib/drivers/ddp.ts`, `send` | `lib/drivers/ddp.send.spec.ts`, the not-open case, driven ten minutes forward on the fake clock | Only the unbounded wait is pinned by a spec. The dropped `throw` cannot be: the rejection escapes as an unhandled rejection and fails the file whatever the test asserts. |
| 8 | `DDPDriver`'s constructor writes `timeout: 10000` into its config *after* spreading the caller's options, so a caller-supplied `timeout` is discarded. Combined with row 3 — the socket reads its ping interval from `timeout` — the number a caller passes reaches nothing at all. | `lib/drivers/ddp.ts`, `DDPDriver` constructor | `lib/drivers/ddp.driver.spec.ts`, `new DDPDriver` | Wrong because it is silent: the option is accepted, typechecks, and is overwritten. Fixing it means letting the caller's value through, which changes the ping interval for anyone who passes one — hence the pin. |
